## 0. Workflow: 4-Gate Software Factory

All features MUST pass through the `docs/plans/<feature>/` workflow. No implementation code is written until Gate 3 is approved.

| Gate | Name | Deliverable | Approval Required |
|------|------|-------------|-------------------|
| 0 | Retrospective | `00-retro.md` — review past commits for tech debt, regressions, contract breaks | ✅ User |
| 1 | Product Spec | `01-product.md` — user stories, scope, success criteria | ✅ User |
| 2 | Architecture | `02-architecture.md` — module design, data flow, route design | ✅ User |
| 3 | Program Design | `03-program-design.md` — API response shapes, TypeScript signatures, contracts | ✅ User (CRITICAL) |
| 4 | Vertical Slices | `04-slices.md` — end-to-end tracer bullets, then real logic per slice | Each slice → `turbo run build` green |

**Golden rules:**
- NEVER build horizontally — always vertical, end-to-end tracer bullets first.
- Compact context into `docs/plans/` markdown files at every gate boundary.
- Stop at every gate and wait for explicit user approval before proceeding.
- `turbo run build` must pass with zero errors before ANY slice is claimed done.

**Module structure:**
```
apps/api/src/
├── main.ts                    # Bootstrap: helmet, validation, swagger
├── app.module.ts              # Root module
├── database/
│   ├── schema.ts              # Drizzle ORM schema (ALL tables + relations + enums)
│   └── database.module.ts     # DB connection provider
├── common/
│   ├── guards/jwt-cookie-auth.guard.ts   # JWT HttpOnly cookie guard
│   ├── decorators/current-user.decorator.ts
│   ├── interceptors/sentry.interceptor.ts  # Sentry error tracking
│   ├── interceptors/logging.interceptor.ts # Pino structured logging
│   └── utils/timestamp.ts               # withTimestamp() helper
└── modules/
    ├── auth/                  # Phone OTP → JWT → Complete Profile
    ├── matches/               # Discovery feed + match detail
    ├── wallet/                # Ledger service
    ├── venues/                # Venue discovery + detail
    ├── users/                 # User profile + stats
    ├── gateway/               # Socket.IO /lobby WebSocket
    └── health/
```

**NestJS Hard Rules:**
1. All new endpoints MUST be guarded with `@UseGuards(JwtCookieAuthGuard)` — unless explicitly public.
2. DTOs first: every controller method must have a class-validator DTO for request bodies AND query params. Use `@ApiProperty()` decorators.
3. DB access: inject `@Inject('DB_CONNECTION') private readonly db: DB` where `DB = PostgresJsDatabase<typeof schema>`.
4. `updated_at` rule: ALWAYS use `withTimestamp()` from `common/utils/timestamp.ts` for any `.update()` call.
5. New services go in `apps/api/src/modules/<name>/` with: `*.module.ts`, `*.service.ts`, `*.controller.ts`, `dto/`.
6. Migrations: edit `schema.ts` → `npm run db:generate` → review → `npm run db:migrate`. GiST indexes require manual SQL in `drizzle/gist_indexes.sql`.
7. Error handling: use NestJS exceptions (`BadRequestException`, `NotFoundException`, `UnauthorizedException`). Never return raw strings.

## 2. API Contract Rule (CRITICAL)

**All NestJS service methods MUST return fully populated relational objects, never bare DB rows.**

This is the single most common source of bugs. The `createMatch` bare row bug is the canonical example: the service returned a raw Drizzle insert result, which lacked joined relations, causing the frontend to crash on missing fields.

### Correct pattern:

```typescript
// ❌ WRONG — bare DB row, no relations
async createMatch(dto: CreateMatchDto, hostId: string) {
  const [match] = await this.db.insert(schema.matches).values({...}).returning();
  return match; // Missing: pitch, host, players — frontend crashes
}

// ✅ CORRECT — fully populated object with all relations
async createMatch(dto: CreateMatchDto, hostId: string) {
  const [match] = await this.db.insert(schema.matches).values({...}).returning();
  // Re-fetch with all relations the frontend contract requires
  return this.findOne(match.id); // findOne loads pitch, host, venue, players
}
```

Every service method must declare its return type explicitly. Controller DTOs must match the service return shape exactly.

## 3. State & Data

| Concern | Technology | Rule |
|---------|-----------|------|
| Server state | TanStack React Query | All API data (match lists, profiles, wallet) — cache, refetch, mutate |
| Client state | Zustand | UI preferences, form drafts, session-only state |
| Form state | react-hook-form + Zod | All form validation — no inline regex |
| URL state | Next.js App Router | Search params, route params for shareable state |

**DO NOT put server-cache data in Zustand.** If it came from the API, it goes through TanStack React Query.

Zustand slices follow the pattern in `store/slices.ts` — each slice is a `createXxxSlice` function receiving a `set` callback. New slices must follow this pattern.

## 4. Observability (MANDATORY)

Every new feature must integrate the observability stack in Slice 3:

### 4.1 Sentry — Error Tracking
- **API**: `SentryInterceptor` catches all unhandled exceptions, attaches user context (userId, phone), and reports stack traces.
- **PWA**: `Sentry.init()` in the browser with React error boundary integration. All API error responses route through a Sentry breadcrumb.
- New endpoints: add `@UseInterceptors(SentryInterceptor)` or use the global interceptor.

### 4.2 Pino — Structured Logging
- **API**: NestJS `Logger` backed by Pino. All logs are JSON-structured with `{ context, userId, requestId }`.
- Log levels: `trace` (dev only), `debug`, `info` (business events), `warn`, `error`, `fatal`.
- Never use `console.log` in production paths — use `this.logger.log()` / `this.logger.error()`.

### 4.3 PostHog — Analytics
- **PWA**: `PostHogProvider` wraps the app. All user actions (page views, button clicks, form submissions) emit PostHog events.
- Event naming: `snake_case`, domain-prefixed (`match_created`, `wallet_topup_initiated`, `profile_updated`).
- New screens: add page-view capture and at least one meaningful action event.

## 5. i18n & PWA

### 5.1 Internationalization
- Every user-facing string MUST have keys in BOTH `ar.json` AND `en.json`.
- Use `next-intl`'s `useTranslations()` hook. Pages are under `[locale]` route group.
- **NO hardcoded strings** in UI components — all must be i18n keys.

### 5.2 RTL/LTR
- Root layout sets `dir` based on locale.
- Use Tailwind logical properties (`ms-*`/`me-*` instead of `ml-*`/`mr-*`) for bidirectional support.
- Test every screen in both Arabic and English.

### 5.3 PWA
- `manifest.json` and `sw.js` must be kept in sync with new routes.
- Icons in `public/icons/`.
- Offline page (`offline.tsx`) must be functional.

## 6. UX States (Mandatory)

Every screen must handle 5 states:
1. **Loading** — Skeleton/spinner (never blank screen)
2. **Empty** — Illustrated CTA (e.g., "No matches yet — find a game")
3. **Populated** — Normal data display
4. **Error** — Retry button + human-readable message
5. **Edge** — Form validation errors, disabled states, rate limits

## 7. Database — Schema & Subagent

### 7.1 Tables (all in `apps/api/src/database/schema.ts`)

| Table | Key Columns | Notes |
|-------|------------|-------|
| `users` | id, phone (unique), full_name, handle (unique), wallet_balance, preferred_position, skill_level, role, karma_score, rating | Wallet uses `numeric(12,2)` |
| `venues` | id, owner_id → users, name, city, location (PostGIS geography) | CASCADE DELETE from users |
| `pitches` | id, venue_id → venues, name, size (enum), surface_type, hourly_rate | CASCADE DELETE from venues |
| `matches` | id, host_id → users, pitch_id → pitches, title, match_type, scheduled_at, price_per_player, max_players, location (PostGIS) | status: Open/Full/InProgress/Completed/Cancelled |
| `match_players` | id, match_id → matches, user_id → users, team (Home/Away), is_host, no_show | Unique constraint on (match_id, user_id) |
| `transactions` | id, user_id → users, type, amount, reference_type, idempotency_key (unique) | Append-only ledger |
| `match_messages` | id, match_id → matches, user_id → users, content | Indexed on match_id |

### 7.2 Database Subagent Rules

When delegating database work, the subagent must:
1. Review schema changes for normalization, correct types, and FK cascade behavior.
2. Never squash or delete applied migrations.
3. Apply GiST indexes after every new database or migration that touches geography columns.
4. Seed data must be idempotent and realistic (≥5 users, ≥3 venues, ≥5 pitches, ≥5 matches).
5. All monetary values use `numeric(12,2)`. PostGIS columns use `geography(Point,4326)`.

## 8. Code Quality Gates

Before claiming ANY work complete:
1. `npm run build` from root — zero errors.
2. `npx tsc --noEmit -p apps/api/tsconfig.json` — zero errors.
3. Tests pass: `npx vitest run` from `apps/player-pwa`.
4. No `any` types in new code.
5. No `console.log` in production paths — use NestJS `Logger` / Pino.
6. No hardcoded strings in UI — all must be i18n keys.
7. No raw `fetch` in PWA components — always use `lib/fetcher.ts`.
